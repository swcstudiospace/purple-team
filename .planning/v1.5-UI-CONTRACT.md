## 4. Agreed API adapter boundaries (proposed, not verified)

**AC:** 005–020, 024, 037–048, 057–060. Owner: A03/API integration. UI has no independent permission logic that replaces the authoritative executor.

### 4.1 Discovery

`GET /api/operators/capabilities?archetype=<exact role>` returns:

- `contractVersion: '1.0.0'`, `roles[]` with `archetype`, `discipline`, `capabilities[]`.
- Each capability: `id`, `toolNames`, `catalogIds`, `mode` (`analysis`, `offline_validation`, `authorized_probe`, `import_only`, `catalog_only`), `availability: {state: available|unconfigured|missing_dependency|unsupported, reason?, nextAction?}`, `inputSchema`, `cancellation: 'unsupported'`.

Treat missing mapping/schema/loadability as unavailable/unknown, not available by absence of a false flag. A role's parent discipline and current capability binding must agree. Catalog IDs are not tool names; separate them visibly. Schema serves valid forms/help and allowed enum/finite bounds; backend validates all again. No implicit opt-in registration, binary install, external service call or credential acquisition from clicking “Configure”. Existing `/api/operators/prompts` loads editable prompt/role descriptions; `/api/teams/tool-grants` metadata is supplemental, not sufficient execution permission. API loading and missing model states are separate: offline dependency-free analysis may remain available if its handler is real, while a model-backed task with no configured model is unconfigured. UI must display the actual per-capability decision, not infer all tasks from global health.

### 4.2 Dispatch and immutable origin

1. User Configure action loads/validates role/capability/context only.
2. User Dispatch freezes an input draft and creates one optional UUID `clientRequestId` for that user submission; it is a reconciliation label, **not a mission/run/evidence ID**.
3. Reuse an available actual operator of the exact role and mission, or explicitly spawn once via existing `POST /api/operators/spawn {archetype,callsign?}`. Spawn acknowledgement is “Operator ready”, not dispatched/completed. If task validation fails after spawn, retain operator identity and inputs; retry task only after correction, not re-spawn blindly. Cannot spawn when mission/role unavailable.
4. Submit existing `POST /api/operators/:id/task` with retained taskName/taskDescription/phase/priority plus required-for-new-hats `capability`, `context`, typed `inputs`, and optional `clientRequestId`.
5. `context = {missionId, target: {kind:'target',targetId} | {kind:'artifacts',artifactIds:[...]}, inputRefs:[{kind:'finding'|'evidence'|'artifact'|'action'|'path'|'retest',id}]}`. Resolve all IDs in the authorized origin; no first-target/global-latest substitution. Raw scope entries and approval text do not authorize context.
6. ACK preserves success/taskId/operatorId/message and adds `runId = taskId`, `origin: {discipline,archetype,operatorId,missionId,target,inputRefs,capability}`, `resultUrl: '/api/operators/tasks/<taskId>'`, `cancellation:'unsupported'`, retained clientRequestId. Validate ACK origin against submitted snapshot. Mismatch is contract/identity error, not a successful result under current selection.
7. Red retains supported original task fields/defaults and public contracts; new typed inputs are not substituted into Red's existing callers. UI uses exact documented Red discovery, not an invented `red.assess` capability.

A03's minimal duplicate safeguard in existing retained runs uses missionId+operatorId+clientRequestId: same normalized inputs return same ACK; changed body yields 409 context_conflict. UI still prevents duplicates locally and does not automatically re-POST on network failure. No new persistence or retry framework.

### 4.3 Results, progress and retention

Authoritative `GET /api/operators/tasks/:taskId` returns `contractVersion`, `taskId`, `runId`, `origin`, `state`, `executionSettled`, `sequence`, `stages`, `evidenceIds`, optional typed `result`/`error`, `limitations`, `retention:'snapshot-no-auto-resume'`, retained clientRequestId. Source proposed states: pending/running/completed/empty/unavailable/failed/partial/interrupted/timed_out. Full redacted result is retained in existing snapshot, not replaced by current global projection. SSE keeps existing events plus runId/origin/sequence/resultUrl; it is a notification to reconcile, not sole proof. Current truncated SSE cannot be advertised as a complete result.

Status tasks add runId/origin/sequence/state/executionSettled/resultUrl/clientRequestId while preserving old fields. For lost ACK, UI marks “Submission outcome unknown; do not submit again”, queries mission status for **exact clientRequestId and operator/mission**, then retrieves result URL and checks origin. No name-only/most-recent matching. Ambiguity or inability to find/settle remains unknown, locks unsafe context changes and offers refresh/reconcile, not speculative retry. After browser reload, a known run URL restores its origin/result. Unknown outcome can retain only safe request/mission/operator identifiers in URL for reconciliation; raw drafts are not promised to survive reload. Snapshot result availability is distinct from automatic runtime resumption; never claim paused/parked/resumable execution just because a result is readable.

Errors retain legacy `error:string` and add `code`, optional `fields:[{field,message}]`, `retryable`, `nextAction`, optional origin. Extend existing shell helpers to preserve these fields on caught errors while maintaining message/string behavior of existing callers. Non-JSON/malformed response is explicit transport/contract error, not an empty clean report. Existing bearer API-base handling remains; new UI uses these helpers, never sends a bearer to a result-provided arbitrary URL. Accept only documented same API-base result path and encode ID segments; do not follow arbitrary output links as authenticated requests. Redaction happens authoritatively; UI never dumps response/request headers or tokens into diagnostics.

### 7.2 Race guards (observable behavior, not implementation recipe)

3. **Role vs filter:** harmless roster text/filter can change during run; it does not change execution selection or origin. 6. **Panel generation:** scoped GET/reconcile reads snapshot mission/filter and generation; late M1 read after M2 selection stays attributed to M1 archive, not M2 card. Display filter empty vs actual dataset empty distinctly.
7. **Navigation/closure:** closing config/editor is not run cancellation. Run card persists within page; known run deep link restores server-retained result on reload. Warn through existing confirmation pattern before abandoning an unsettled/unknown submission draft; browser navigation does not claim execution ended.
8. **Retries:** no automatic execution retry from a generic `[data-retry]` listener, timers, SSE reconnect or capability load. Keep prior result; renewed input/approval generates a distinct reassessment linked to previous evidence, never re-labels old evidence as newly observed. Do not promise repeating completed side effects is safe without backend reconciliation.
9. **Scheduler scope:** stop/pause/resume are separate from task/run state; mission active:false does not settle a run. Once actual operation settles, safe switching unlocks. If it never settles within reported bounds, show explicit unconfirmed limitation, not a fabricated cancel.
