## 2. Minimal C4 blueprint and dependency direction

**Context:** one authorized operator uses the existing local/static War Room, MCP proxy or published instruction skill. These clients request existing mission/operator actions. Models, artifacts, imported frameworks and reports are untrusted evidence producers, not permission authorities.

**Containers:** retain Node/TypeScript API/command process; static HTML/CSS/JS `/ui`; existing MCP stdio/HTTP proxy; optional configured LLM providers/local agents; optional installed local validation binaries; existing redacted state snapshot and ledgers. No service, database, broker, collaboration layer or deployment is added.

**Components and call chain:**

```text
Existing UI / MCP / published skills
  -> server.ts existing origin/Host/bearer/rate guards
  -> validate role + capability + selected mission/target/input IDs
  -> freeze resolved input snapshot and server-issued origin
  -> TempestCommand.dispatchTask -> existing TaskQueue + OperatorAgent.assignTask
       -> Red: unchanged role-bound AgentLoop/LLM route
       -> Blue: blue/workflow.ts sentinel + warden composition
       -> Black: black/workflow.ts specter + wraith composition
       -> White: white/workflow.ts arbiter + auditor composition
            -> permitted registered CustomTool
            -> Arsenal role/scope/approval/argument boundary
            -> pure existing team engines or explicit local validator
       -> immutable typed result + stage/evidence receipts
  -> existing server snapshot operatorTaskRuns + existing evidence/retest ledgers
  -> GET task result / SSE notification / mission status
  -> explicit Purple synthesize (read-only combine selected run references)
```

Dependency rules: clients never duplicate scoring/permissions; server/command may import teams, not vice versa. `src/teams/contracts.ts` (new) contains only shared types/constants/validation descriptions, no server globals/HTTP/model IO. Per-hat workflows import their own engines and existing pure specialist functions; they accept resolved context and injected bounded IO, never query latest/global state. `src/teams/hats.ts` remains the public specialist functions/identity boundary; its single integration owner fixes shared semantics after per-hat work, not three concurrent editors. No new hat-count registry overrides `OperatorArchetype`. Existing resources may be consumed by teams/prompts; resources must not import executable workflow or server authority.

Purple stays an explicit call with no automatic operator spawn, result subscription dispatch, verdict auto-consumption or delegated grants. It does not join the spawnable union. A White verdict can constrain/recommend; it cannot mint an approval receipt.

### Pre-handler validation without violating existing schema depth

Existing `CustomTool` gains optional `validateArguments(parameters: Record<string,unknown>, context: ToolContext): ToolValidationError[]`. Arsenal calls existing validateToolArgs and this synchronous domain validator **before** invoking `handler`; violations become ValidationError with redacted field paths, never received secrets. Existing shallow scalar coercion does not apply to domain payloads. Deep DTO validation is compiled once using existing AJV, with finite semantic checks for IDs/numbers/ref membership after schema validation. No new validation package, no raising MAX_SCHEMA_DEPTH, no custom script evaluator.

For new workflow tools, `parameters` expose their documented top-level fields (arrays/objects and leaf discriminants) within depth three; `validateArguments` enforces the complete schemas below. Discovery `inputSchema` is the full compiled DTO schema, with `$id` `t3mp3st.fh.<capability>/1.0.0`; arrays/objects do not become unvalidated because offered tool schema is shallow. API and MCP validate the same exported schemas, and handler entry is still guarded for direct internal calls. Validators export `validateBlueInput`, `validateBlackInput`, `validateWhiteInput` from their respective workflow modules; they return the existing ToolValidationError[] and never perform IO.

Common rules: no coercion of string numbers/bools; all numerical quantities finite; all IDs nonblank and unique in their declared collection; dangling/duplicate/conflicting refs rejected rather than dropped. Reject unsafe prototype keys and unexpected fields on semantic DTOs. Limits use existing request cap/configured bounds; semantic leaf limits for this local contract: ID length ≤128, objective ≤16,384 chars, at most 256 selected findings/actions/paths/controls/telemetry sources, 256 cases per detector and 1,024 selected evidence/artifact refs; ROE keeps existing 64 KiB cap. These are deliberate bounded-input contract decisions, not measured capacity claims. Domain validation reports the exact field, e.g. `inputs.paths[1].volumeMb`; it does not echo full artifact or secret values. Oversized body 413 precedes work. Missing syntactically required field is invalid_input; syntactically valid selected ID that cannot resolve in authorized context is missing_input/not_found, never an empty clean report.

FieldPredicate accepts dot-separated **own-property** field keys only. Reject `__proto__`, `constructor`, `prototype`, empty segments, expressions, wildcard selectors, regex, JS/eval and recursive object comparison. equals requires a scalar value and strict value/type equality; contains requires string value and actual string; exists omits value and distinguishes own presence from truthiness (false/0/null are present). Missing value cannot match equals/contains. JSON records are parsed as data. This provides real, explicit offline detector/control replay without pretending to evaluate all Sigma or arbitrary code.

### Honest availability

Capability discovery is passive/read-only; do not health-probe remote targets/models to calculate availability. State is one of available, unconfigured, missing_dependency, unsupported with `reason` and `nextAction`; mode is analysis, offline_validation, authorized_probe, import_only, catalog_only. “Available” means registered + role permitted + local prerequisite known, not a successful execution verdict. ## 5. Immutable mission/task/result binding and honest lifecycle

### Smallest real task/retention addition

1. Existing `/api/operators/:id/task` checks actual operator, role/capability, mission and all context IDs before emitting dispatched or starting execution. New hats require explicit context and structured input; no missionId='manual', first target, latest mission, prose substring or unrestricted global reads. Red legacy request omission may resolve the existing active mission/first-target convention **once at acceptance**, then freeze and report it; explicit context always takes precedence, cannot silently fall back.
2. Resolve target ID through that mission's actual TargetEnvironment; artifact-only context is explicit and cannot grant network authority. Resolve input refs through authorized existing mission/operation/evidence records or explicitly submitted imported objects. Imported inline findings/actions are marked claimed/context-grade, assigned stable submitted IDs and bound as data; duplicate inline-vs-ledger conflicting ID content is context_conflict. No client-supplied `approved`, provenance strength, egressVerified or scope can overwrite trusted state.
3. Snapshot normalized input once (copy/freeze only at acceptance, not every tool call). `origin` is readonly and server-issued with actual operator role, discipline, capability, mission, target/input refs. Add task to existing TaskQueue, pin `assignedTo`, then use one command-owned `dispatchTask(taskId, operatorId)` for scheduler and manual tasks. Reserve/assign atomically before async work so simultaneous requests cannot both see idle. No queue race or duplicate fire-and-forget path.
4. Proposed command exports `submitOperatorTask(operatorId, request): DispatchAck`, `getTaskRun(taskId): TaskRunView|undefined`, `getTaskRunViews(missionId): readonly TaskRunView[]`. HTTP invokes these; it does not directly call assignTask and maintain a second executor. Queue remains execution source of truth. The command has a bounded per-dispatch timeout monitor independent of paused/stopped scheduler ticks for manually accepted tasks; it uses the existing resolved taskTimeoutMs, not a new unbounded policy.
5. Preserve the complete redacted TaskResult/WorkflowResult, not only truncated SSE prose. Server adds `operatorTaskRuns` to existing buildStateSnapshot/restore under the same `t3mp3st_state/v1` snapshot, backward-compatible absent slot. It is the retained read projection of task origin/stages/result, not a second working queue. Existing evidence/retest ledgers store applicable receipt IDs; no long-lived credentials/raw sensitive input are added. Retention is explicit `snapshot-no-auto-resume`; original normalized inputs may be retained in the existing run record after redaction when safe, but the UI does not persist raw bodies in localStorage.
6. On restore, validate every retained row before serving it; legacy snapshot lacking rows loads Red unchanged. Any row pending/running at process loss becomes interrupted and executionSettled:true because the old process cannot continue, with “restart interrupted; no automatic resume.” Retained outputs/evidence remain, but the old command's live mission/report availability is not invented. Historical result retrieval may work while report generation for that old runtime mission remains unavailable; distinguish them.
7. Event/result writes carry monotonic sequence, task ID and origin. Late results cannot retarget new mission or overwrite a terminal timeout; retain usable late evidence as late/partial under original run with limitations and advance sequence, never convert timeout into full success. A truthfully timed-out observation can have executionSettled:false until the underlying promise/subprocess actually settles. Do not reset/reuse an unsettled operator for another dispatch merely to make UI appear idle.

### Concrete workflow and semantics

1. Prerequisites: resolve requested mission/findings/artifacts/evidence, detector/rule inputs and domain. An explicit empty findings collection yields empty; unknown finding ID is missing_input. Resolve only selected evidence; telemetry registry is guidance, not evidence that sensors are deployed.
2. Inventory: annotate supplied telemetry as **declared** separately from observed logs/receipts. Do not conflate existing TelemetryDeclaration fields with registry entries.
3. A declared source/coveredIds alone cannot satisfy verified coverage. Existing legacy projections may retain declared labels but must expose evidenceStanding claimed and cannot be reused as proof; new workflow gaps derive observed semantics and cite actual evidence IDs/limitations.
4. Detector validation: execute supported local replay on submitted positive and negative cases, retain rule hash/tool identity/version when known, case input IDs/hashes, actual expected/observed outcomes and receipt IDs. Missing positives or negatives returns unavailable/missing_input for a claim of validated detection, not success based on one happy example. A detector is validated only when both classes run and meet expected outcomes; failed cases remain listed.
5. Field-match replay: parse authorized supplied JSON-record artifact, evaluate own-property predicate on each record, count/match with expectation and generate actual local-computation receipt. No model/network/binary needed. This is a supported exact-field detector/control engine, not mislabeled general Sigma support.
6. YARA: correct operation contract `{ruleArtifactId,sampleArtifactId}`; both contained registered local artifacts. Use existing optional `yara` binary with hardcoded argv, private copies and finite timeout/output cap; do not execute the sample, recursively scan arbitrary directories or permit user flags. Compile/match errors are failed; missing binary is unavailable; output maps actual matching rule IDs and expected/observed case results. Real benign and matching fixtures prove it. Generic single target invocation is not retained as an advertised rule-validation implementation.
7. Sigma: correct `{ruleArtifactId,operation:'check'}` maps to installed `sigma check <contained-rule-file>` with hardcoded argv and exit/diagnostic receipt. This validates syntax, **not** log replay. There is no YAML parser dependency in package.json and sigma-cli alone does not prove a replay engine. Candidate Sigma detector with cases therefore reports syntax result plus replayStatus unsupported unless an existing installed supported conversion/replay prerequisite genuinely resolves; no invented pySigma/SIEM API or new dependency. Supported field_match/YARA replay fulfills real offline replay; Sigma cannot be advertised as validated detection merely because syntax passes. Its unavailable replay remains a visible gap until actual prerequisite/evidence or explicit accepted role asymmetry; no silent scope reduction or completion credit.
8. Hardening: generated severity-tier suggestions are open controls. Submitted controls retain stable item ID, finding IDs, priority, baseline evidence and exact verification predicate. Resolve only when baseline demonstrates the relevant failure, after demonstrates expected fixed state, required evidence is sufficient and IDs/hashes match. Proposed fixes/checklists alone remain open/insufficient; failed retest stays unresolved. Do not change target config or call a live endpoint to fill missing artifact.

Parent Blue composes Sentinel and Warden only; missing one stage is partial, not a successful combined control closure. Reassessment consumes linked new artifacts/retests, never global ledger latest.

Domain allocations: web/API uses supplied request/response/header/CSP/cookie/auth logs; cloud uses supplied config/IAM/cloud audit artifacts; code/supply-chain uses supplied source/SBOM/static scanner outputs; secrets uses redacted secret-scanner findings, never secret values; AI uses supplied prompt/retrieval/model transcripts; agent warfare uses tool authority, memory/RAG and action logs. Corpus validation instructions involving live EDR/Atomic tests are described as prerequisites/alternatives, not executed. Every supported domain has role guidance plus a genuine local analysis output and a forbidden-probe oracle.
